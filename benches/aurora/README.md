# AURORA: the benchmark suite

One suite and one runner for Codira's performance against Rust and C++:
each workload is a Codira program and a Rust and a C++ baseline that do
the same work and print the same check value, built with recorded flags,
run in interleaved processes, and reported as medians with confidence
intervals, together with peak memory, the Codira GC heap, latency
percentiles where a workload has requests, `perf stat` counters where
`perf` works, compile time and binary size.

`RESULTS.md` is the first full run, on the machine described there, with
every number and its interval. Later work measures against it.

## Layout

```
benches/aurora/
  suite.toml            every workload and kernel; the CI subset; heap caps
  README.md             this file
  RESULTS.md            the reference run
  baseline/ci.json      the regression gate's stored baseline
  host/                 runs one kernel of a Codira library (heap cap, RSS, GC stats)
  common/bench.rs       what the Rust baselines share (clock, report line, RNG)
  common/bench.hpp      the same for the C++ baselines
  <workload>/
    codira.toml, src/mod.code     the Codira program: one public function per kernel
    <workload>.rs                 the Rust baseline (one `rustc` invocation),
    rust/                         or a Cargo project when it needs crates (json)
    <workload>.cpp                the C++ baseline
scripts/bench.py        the runner
.github/workflows/aurora-bench.yml   the opt-in and weekly gate
```

The workloads:

| workload | what | kernels |
|---|---|---|
| `strings` | append, concatenation, splitting (into arrays and lazily), search, parsing | 9 |
| `format` | integers and floats to text, format specs, the debug form | 5 |
| `json` | parse, print, pretty-print three inputs (`gen_inputs.py`) | 9 |
| `hashmap` | insert, lookup, churn with Codira's hash in all three; Rust's default SipHash separately | 10 |
| `result` | `?` wrapping, converting to `AnyError`, with context, eight frames deep | 5 |
| `collections` | push, sum, sort, eager and lazy pipelines over 10M elements | 13 |
| `loops` | numeric loops, field stores, copies, recursion, sieve, float and branchy loops | 9 |
| `graph` | allocation-heavy binary trees, cyclic graphs, a doubly linked list | 3 |
| `channels` | producers and consumers over bounded channels | 3 |
| `server` | request handling with high churn, per-request latency; long runs under GC heap caps of 1024 down to 64 MiB | 7 |

and, for every workload, compile time and binary size.

They replace the benchmarks that were scattered over the repository
(`examples/collections_bench`, `collections_loop_cost`, `pipelines_bench`,
`format_bench`, `error_bench`, `json_bench` and `benches/strings`), whose
programs became kernels here. `benches/benches` (criterion: the compiler
and runtime against Lua and Wasm, `scripts/bench.sh`) and `codira bench`
(a package's own `@bench` functions) are separate tools and stay.

## Running it

```bash
cargo build --release -p codira               # the compiler under test
python3 scripts/bench.py                      # the full suite (about an hour here)
python3 scripts/bench.py --suite ci           # the CI subset (minutes)
python3 scripts/bench.py --only strings. --only format.int   # kernels by id
python3 scripts/bench.py --runs 21 --variants codira,rust     # more runs, no C++
```

It needs Python 3.11+ (standard library only), a release `codira`
(`--codira` to point elsewhere), `cargo` and `rustc`, a C++23 compiler
(`clang++-22` if present, `--cxx` to choose), `g++` and RapidJSON
(`rapidjson-dev`) for the JSON baseline, and optionally `perf`. A variant
that cannot be built is reported with the reason, not dropped silently.
Build products go under `--work` (default `target/aurora`); results under
`<work>/results/<date>/`: `results.json` (every sample, every build
command, the machine) and `summary.md` (the tables).

## Method

- **Same semantics.** The three programs of a kernel compute the same
  thing from the same inputs, generated by the same seeded xorshift
  generator, and print a check value; the runner compares them and fails on
  a mismatch. A known, explained difference is declared in `suite.toml`
  (`check_differs`) and reported. Where a Codira feature a kernel needs does
  not exist yet, the kernel is in the suite with its baselines and the
  Codira variant marked as not yet possible, with the reason (the
  `*_secure` hash map kernels: `Map` has no seeded hasher). A kernel known
  not to complete today is declared (`expected_failure`) and reported as
  such; the runner says so when it starts to complete.
- **What is timed.** Each kernel times its own work with a monotonic clock
  and prints `@@ ns=<n> check=<c>`; setting up the input is outside the
  timing. Each run is a fresh process, so no kernel sees another's heap,
  caches or allocator state. Codira kernels run in `benches/aurora/host`, a
  release build of the runtime with a GC heap cap (`heap_limit_mb`, 1 GiB
  by default, lower for the allocation-heavy workloads): without a cap the
  collector never runs.
- **Interleaving.** One warm-up round (discarded: page cache, binaries,
  input files), then `--runs` rounds (11 for the full suite, 9 for CI). In
  every round all selected (kernel, variant) pairs run once, in an order
  shuffled with a seeded generator, so drift in the machine's speed spreads
  over all variants instead of landing on one.
- **Statistics.** The median of the runs, with a 95% percentile-bootstrap
  interval for the median (2,000 resamples). Ratios are Codira's median
  over the baseline's, with a bootstrap interval resampling both sides.
  Every kernel is reported on its own: there is no aggregate score.
- **Memory and pauses.** The peak resident set of the process (`VmHWM` at
  exit, read by the program or the host; the runner falls back to `wait4`).
  For Codira, the host prints `Runtime::stats()` after the kernel: the
  heap's peak, the live bytes after the last collection, bytes allocated,
  collections by cause (paced or at the cap), the time the world was
  stopped and the time to reach a safepoint, and the pause count, median,
  99th percentile and maximum. The collector runs with the runtime's
  default pacing (the next collection at 100% growth over the live data)
  under the kernel's cap, as under `codira run`.
- **Latency.** The `server` workload times each request and prints the
  p50, p95, p99, p99.9 and maximum; the tables give the median of each over
  the runs, with an interval.
- **Counters.** `perf stat -e cycles,instructions,cache-misses,
  branch-misses,context-switches,cpu-migrations,page-faults,task-clock`
  around each process, where a `perf` that runs on the kernel exists
  (`AURORA_PERF` to name one). Events the machine cannot count are listed
  as not available with the reason; most virtual machines expose no
  hardware counters, only the software ones. `--no-perf` turns it off.
  Counters cover the whole process, start-up included.
- **Compile time and binary size.** `--compile-runs` (5) from-scratch
  builds of every variant, in shuffled order: `codira build -O 3` (its
  output directory removed first; the size is every `.codiralib` written,
  one per imported standard-library module, without the runtime), one
  `rustc` invocation, one C++ compiler invocation (size as built and
  stripped).
- **Recorded.** The CPU, logical CPUs, memory, OS, kernel, virtualization,
  frequency governor, load average at the start and the end, the commit and
  whether the tree had changes, the `codira` binary's hash, and every
  toolchain's version and flags: Codira `build -O 3`, Rust `--edition 2021
  -C opt-level=3 -C codegen-units=1`, C++ `-O3 -std=c++23 -pthread
  -DNDEBUG`, all for the default (generic x86-64) target.

What the numbers are not: the runner does not pin CPUs, isolate cores or
fix the clock frequency, and the machine behind `RESULTS.md` is a shared
virtual machine. Results are comparable within one run and between runs on
the same machine class; absolute times on another machine are not.

## The regression gate

`python3 scripts/bench.py --suite ci --baseline benches/aurora/baseline/ci.json`
runs the CI subset (the kernels marked `ci = true`) and compares each with
the stored baseline:

- The metric is the **per-round ratio** of Codira's time to Rust's time
  (the two ran in the same round, close together), or Codira's time alone
  for a kernel without a Rust variant. The ratio removes most of the
  difference between machines and between a quiet and a loaded moment.
- For each kernel, a **one-sided Mann-Whitney U test** asks whether the
  current ratios tend to be larger than the baseline's.
- The p-values are **Holm-corrected** over the kernels, for a family-wise
  error rate of `--alpha` (0.05): with thirty kernels, a fixed per-kernel
  threshold would report a false regression in most runs.
- A kernel **regresses** when its test survives the correction *and* the
  bootstrap 95% interval of the change in the median ratio lies above
  zero. There is no fixed percentage threshold.
- A regression makes the runner exit with status 3; a check value mismatch
  or a failed kernel with status 1. The table of every test is in the
  summary.

The workflow `.github/workflows/aurora-bench.yml` runs it on demand
(Actions, "AURORA benchmarks", `suite: ci`) and every Sunday; it is not part
of the main CI.

### Updating the baseline

Update it when a change makes Codira faster for good (an improvement would
otherwise hide a later regression of the same size), when the gate's
machine class changes, or when a kernel in the CI subset changes:

1. Run the workflow with `save_baseline: true` (the gate's own machine
   class), or locally on the machine that will run the gate:

   ```bash
   python3 scripts/bench.py --suite ci --save-baseline benches/aurora/baseline/ci.json
   ```

2. Check the run's summary: every check value "same", no failure, and no
   kernel slower than you expect.
3. Commit `benches/aurora/baseline/ci.json` with a message that says why
   the baseline moved and which kernels changed.

The baseline holds every sample with its round, so it can be compared
with any later run; it is small (a few hundred kilobytes).

## Adding a workload

Add a directory with `codira.toml`, `src/mod.code` (one `public func
<kernel>()` per kernel, each printing `@@ ns=.. check=..` as the others
do), `<name>.rs` and `<name>.cpp` (taking the kernel name as their first
argument), and a `[[workload]]` entry in `suite.toml`. Make the check value
depend on all the work, generate inputs with the shared xorshift
generator, keep set-up outside the timing, and make sure the baselines are
what a competent programmer in that language would write: the suite exists
to show where Codira loses.
